# Task Tracker

## О проекте

Task Tracker помогает студенту вести личные задачи. Пользователь добавляет задачу, указывает срок, меняет статус и находит просроченные записи.

## Запуск

Из корня скачанного проекта:

```bash
cd frontend
npm ci
```

Затем создайте `frontend/.env.local` по образцу `frontend/.env.example` (раздел «Настройка Supabase») и запустите:

```bash
npm run dev
```

После запуска открыть адрес, указанный Vite в терминале. Без `.env.local` приложение запускается, но форма сообщает об ошибке настройки и не даёт сохранить задачу.

## Проверка сборки

Остановите dev-сервер через `Ctrl+C`. Выполните в папке `frontend`:

```bash
npm run build
npm run preview
```

## Что работает сейчас

* общий layout с навигацией (React Router) и заметкой о временном хранении данных;
* общий список задач в состоянии `App` (`useState`); начальные данные берутся из `data/tasks.ts`;
* **создание** задачи (`/tasks/new`), **просмотр** (`/tasks/:id`), **редактирование** (`/tasks/:id/edit`) и **удаление** с подтверждением (`window.confirm`);
* одна переиспользуемая форма `TaskForm` с отдельным черновиком: «Отмена» ничего не сохраняет;
* проверка ввода: название 3–100 символов (пробелы обрезаются), обязательный срок; предметное правило — у задачи со статусом «Готово» должно быть описание результата (просроченный срок допустим);
* фильтр списка по статусу и кнопка «Сбросить фильтр»; различаются пустой список и отсутствие совпадений;
* страницы для неизвестного адреса и отсутствующей задачи;
* **тег задачи выбирается из справочника в Supabase** (таблица `public.tags`, чтение через `supabase-js`), с состояниями загрузки, ошибки и пустого результата, кнопками «Повторить» и «Обновить справочник» и запретом сохранения без допустимого тега;
* строгая проверка типов TypeScript (`strict`) и production-сборка.

## Настройка Supabase

1. Создайте учебный проект в Supabase Dashboard (пароль базы храните в менеджере паролей).
2. В **SQL Editor** выполните целиком `supabase/migrations/202610242011_initial_schema.sql`, затем `supabase/seed.sql`. Порядок обязателен: seed вставляет строки в таблицу, созданную миграцией.
3. В Dashboard откройте **Connect** (или **Settings → API Keys**) и скопируйте URL проекта и publishable key.
4. Создайте `frontend/.env.local` по образцу `frontend/.env.example`. Используются две переменные:

| Переменная | Что хранит |
|---|---|
| `VITE_SUPABASE_URL` | адрес проекта Supabase |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | publishable key проекта |

5. Перезапустите Vite: значения подставляются при запуске и сборке.

Переменные `VITE_` попадают в собранный JavaScript, поэтому допустим **только publishable key**. Secret key, `service_role` и пароль базы данных во frontend, в репозиторий и на скриншоты не попадают. `.env.local` исключён из Git (`.gitignore`), `.env.example` — в репозитории и содержит заглушки.

## Схема данных (ЛР 5)

| Таблица | Назначение | Ключ | Связь | Данные |
|---|---|---|---|---|
| `tags` | справочник тегов | `id` (text, стабильный код) | — | **публичные**, только чтение |
| `tasks` | задачи пользователя | `id` (uuid) | `tag_id` → `tags.id` (`on update cascade`, `on delete restrict`); `owner_id` → `auth.users.id` (`on delete cascade`) | **личные**, закрыты от браузера до ЛР 6 |

Ограничения: `tags` — `id` и `name` не пустые и без пробелов по краям, `name` уникально; `tasks` — название 3–100 символов, `status` ∈ {`todo`, `in_progress`, `done`}, `priority` ∈ {`low`, `medium`, `high`}, у задачи со статусом `done` описание не пустое (то же правило, что в форме ЛР 3). Поле `tag` во frontend соответствует `tag_id` в БД и будет преобразовано при переносе задач в ЛР 6.

Доступ: на обеих таблицах включён Row Level Security. Роли `anon` и `authenticated` получили только `SELECT` справочника `tags` и политику чтения; у `tasks` нет ни прав, ни политик, поэтому браузер не может читать или менять личные строки. Схема и права описаны только в миграции, справочные данные — только в `seed.sql`; постоянные изменения вносятся в эти файлы, а не только в Dashboard.

## Справочник тегов (ЛР 5)

Источник справочника — таблица `public.tags` в Supabase. Запрос `GET /rest/v1/tags` к домену проекта виден в Network. Статический `public/demo/tags.json` из ЛР 4 удалён, резервного массива в коде нет: ошибка Supabase показывается в форме. Элемент справочника: `{ "id": "study", "name": "Учёба" }`, где `id` — постоянный код, `name` — название для пользователя (его можно менять в БД без изменения `id`).

| Файл | Назначение |
|---|---|
| `supabase/migrations/202610242011_initial_schema.sql` | таблицы, ограничения, RLS, права, политика чтения |
| `supabase/seed.sql` | справочные данные (UPSERT, можно запускать повторно) |
| `src/lib/supabase.ts` | единственный клиент Supabase, проверка переменных окружения |
| `src/vite-env.d.ts` | типы переменных `VITE_SUPABASE_*` |
| `src/types/tag.ts` | тип `Tag` |
| `src/services/tags.ts` | `getTags` (запрос к Supabase, отмена через `AbortSignal`, проверка `error`), `parseTags` (проверка структуры и уникальности `id`) |
| `src/hooks/useTags.ts` | состояния `loading` / `error` / `success`, повторный запрос, отмена в очистке эффекта |
| `src/components/TaskForm.tsx` | `select` тега, сообщения о состоянии, кнопки «Повторить» и «Обновить справочник», блокировка сохранения |

В `Task.tag` хранится **`id`** тега (например, `study`), в форме показывается `name` («Учёба»). Если сохранённый `id` не найден в справочнике, форма показывает сообщение и не подставляет другой тег автоматически. Недоступность справочника блокирует только сохранение формы; просмотр списка, переходы, отмена и удаление работают. Повтор запроса и обновление справочника не сбрасывают введённый черновик.

## Ограничение: данные только в памяти

Основные записи (задачи) по-прежнему живут в состоянии компонента `App`; из Supabase загружается только публичный справочник тегов. Внутренние переходы между страницами изменения сохраняют, но **после обновления страницы или перезапуска приложения возвращаются демонстрационные записи** из `frontend/src/data/tasks.ts`. Это сделано намеренно: таблица `tasks` создана, но закрыта от браузера и пуста, анонимная запись не открывалась. Supabase Auth и безопасное хранение личных задач появятся в ЛР 6; `localStorage` не используется.

## Текущие ограничения

Нет авторизации (Supabase Auth — ЛР 6) и Node API; задачи не сохраняются между перезагрузками. В Supabase хранится только публичный справочник; таблица `tasks` пока недоступна клиенту. Для работы формы нужен доступ к интернету и заполненный `.env.local`.

## Использование ИИ

ИИ использовался для объяснения структуры React-проекта, проверки соответствия проекта требованиям лабораторной работы и поиска возможных ошибок. Предложенные изменения были проверены вручную по содержимому проекта, запуску и сборке. В ЛР 5 ИИ использовался для подготовки SQL-миграции, клиента Supabase и документации; пароль базы, secret key, `service_role` и содержимое `.env.local` ИИ не передавались.
