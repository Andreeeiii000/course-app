# Task Tracker

## О проекте

Task Tracker помогает студенту вести личные задачи. Пользователь добавляет задачу, указывает срок, меняет статус и находит просроченные записи.

## Запуск

Из корня скачанного проекта:

```bash
cd frontend
npm ci
```

Затем создайте `frontend/.env.local` по образцу `frontend/.env.example` (раздел «Настройка Supabase») и запустите:

```bash
npm run dev
```

После запуска открыть адрес, указанный Vite в терминале. Без `.env.local` приложение запускается, но страница входа и форма задачи сообщают об ошибке настройки; войти и сохранить задачу нельзя.

## Проверка сборки

Остановите dev-сервер через `Ctrl+C`. Выполните в папке `frontend`:

```bash
npm run build
npm run preview
```

## Что работает сейчас

* **регистрация и вход по email и паролю** (Supabase Auth, страница `/auth`), сценарий с подтверждением email (после регистрации без сессии показывается инструкция), выход из текущего браузерного сеанса;
* **защищённые маршруты**: `RequireAuth` пропускает только вошедшего пользователя, пока сессия проверяется — статус «Проверяем сессию…», гость перенаправляется на `/auth`; сессия восстанавливается после перезагрузки;
* общий layout: навигация, email текущего пользователя и кнопка «Выйти»;
* **личные задачи хранятся в Supabase** (таблица `public.tasks`): список, создание, просмотр, редактирование и удаление с подтверждением работают через `supabase-js`, после изменения список загружается заново; данные сохраняются после перезагрузки и повторного входа;
* доступ к строкам ограничен в базе: четыре отдельные политики RLS (`select`, `insert`, `update`, `delete`) с условием `owner_id = auth.uid()`; `owner_id` задаёт БД, браузер его не передаёт;
* состояния загрузки и ошибок: «Загружаем задачи…», сообщение с кнопкой «Повторить», блокировка кнопок на время запроса, черновик формы не теряется при ошибке; при выходе и смене аккаунта список очищается до запроса нового;
* одна переиспользуемая форма `TaskForm` с отдельным черновиком: «Отмена» ничего не сохраняет;
* проверка ввода: название 3–100 символов (пробелы обрезаются), обязательный срок; предметное правило — у задачи со статусом «Готово» должно быть описание результата (просроченный срок допустим);
* фильтр списка по статусу и кнопка «Сбросить фильтр»; различаются пустой список и отсутствие совпадений;
* страницы для неизвестного адреса и отсутствующей (или недоступной) задачи: ответ одинаков, существование чужого id не раскрывается;
* **тег задачи выбирается из справочника в Supabase** (таблица `public.tags`, чтение без входа), с состояниями загрузки, ошибки и пустого результата, кнопками «Повторить» и «Обновить справочник» и запретом сохранения без допустимого тега;
* строгая проверка типов TypeScript (`strict`) и production-сборка.

| Действие | Где |

| Изменить задачу | «Редактировать» на странице задачи |
| Удалить задачу | «Удалить» на странице задачи (с подтверждением) |
| Отфильтровать по статусу | выпадающий список над списком, «Сбросить фильтр» |

## Адреса страниц

| Адрес | Страница |
|---|---|
| `/` | перенаправление на `/tasks` |
| `/auth` | вход и регистрация (публичная; вошедшего пользователя перенаправляет на `/tasks`) |
| `/tasks` | список задач с фильтром (нужен вход) |
| `/tasks/new` | создание задачи (нужен вход) |
| `/tasks/:id` | подробности задачи, `id` — uuid строки БД (нужен вход) |
| `/tasks/:id/edit` | редактирование задачи (нужен вход) |
| любой другой | «Страница не найдена» |

Без сессии все адреса `/tasks…` перенаправляют на `/auth`.

## Настройка Supabase

1. Создайте учебный проект в Supabase Dashboard (пароль базы храните в менеджере паролей).
2. В **SQL Editor** выполните по одному разу и в таком порядке: `supabase/migrations/202610242011_initial_schema.sql`, `supabase/seed.sql`, затем `supabase/migrations/202611151200_tasks_owner_policies.sql` (ЛР 6). Порядок обязателен: seed вставляет строки в таблицу, созданную первой миграцией, а политики владельца накладываются на уже созданную `tasks`. Применённые миграции не редактируются.
3. В Dashboard откройте **Authentication** и проверьте: вход по email и паролю разрешён; подтверждение email оставьте так, как решил преподаватель; в **URL Configuration** адрес Vite (например, `http://localhost:5173`, порт может отличаться) указан в Site URL и добавлен в Redirect URLs — иначе ссылка из письма не вернёт в приложение.
4. В Dashboard откройте **Connect** (или **Settings → API Keys**) и скопируйте URL проекта и publishable key.
5. Создайте `frontend/.env.local` по образцу `frontend/.env.example`. Используются две переменные:

| Переменная | Что хранит |
|---|---|
| `VITE_SUPABASE_URL` | адрес проекта Supabase |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | publishable key проекта |

6. Перезапустите Vite: значения подставляются при запуске и сборке.

Переменные `VITE_` попадают в собранный JavaScript, поэтому допустим **только publishable key**. Secret key, `service_role` и пароль базы данных во frontend, в репозиторий и на скриншоты не попадают. `.env.local` исключён из Git (`.gitignore`), `.env.example` — в репозитории и содержит заглушки.

## Схема данных (ЛР 5)

| Таблица | Назначение | Ключ | Связь | Данные |
|---|---|---|---|---|
| `tags` | справочник тегов | `id` (text, стабильный код) | — | **публичные**, только чтение |
| `tasks` | задачи пользователя | `id` (uuid) | `tag_id` → `tags.id` (`on update cascade`, `on delete restrict`); `owner_id` → `auth.users.id` (`on delete cascade`) | **личные**, открыты только владельцу (ЛР 6) |

Ограничения: `tags` — `id` и `name` не пустые и без пробелов по краям, `name` уникально; `tasks` — название 3–100 символов, `status` ∈ {`todo`, `in_progress`, `done`}, `priority` ∈ {`low`, `medium`, `high`}, у задачи со статусом `done` описание не пустое (то же правило, что в форме ЛР 3). Поле `tag` во frontend соответствует `tag_id` в БД; преобразование `snake_case` ↔ `camelCase` выполняет `src/services/tasks.ts`.

Доступ в ЛР 5: на обеих таблицах включён Row Level Security; роли `anon` и `authenticated` получили только `SELECT` справочника `tags`, у `tasks` не было ни прав, ни политик. В ЛР 6 доступ к `tasks` открыт владельцу — см. раздел «Модель доступа». Схема и права описаны только в миграциях, справочные данные — только в `seed.sql`; постоянные изменения вносятся в эти файлы, а не только в Dashboard.

## Справочник тегов (ЛР 5)

Источник справочника — таблица `public.tags` в Supabase. Запрос `GET /rest/v1/tags` к домену проекта виден в Network. Статический `public/demo/tags.json` из ЛР 4 удалён, резервного массива в коде нет: ошибка Supabase показывается в форме. Элемент справочника: `{ "id": "study", "name": "Учёба" }`, где `id` — постоянный код, `name` — название для пользователя (его можно менять в БД без изменения `id`).

| Файл | Назначение |
|---|---|
| `supabase/migrations/202610242011_initial_schema.sql` | таблицы, ограничения, RLS, права, политика чтения |
| `supabase/seed.sql` | справочные данные (UPSERT, можно запускать повторно) |
| `src/lib/supabase.ts` | единственный клиент Supabase, проверка переменных окружения |
| `src/vite-env.d.ts` | типы переменных `VITE_SUPABASE_*` |
| `src/types/tag.ts` | тип `Tag` |
| `src/services/tags.ts` | `getTags` (запрос к Supabase, отмена через `AbortSignal`, проверка `error`), `parseTags` (проверка структуры и уникальности `id`) |
| `src/hooks/useTags.ts` | состояния `loading` / `error` / `success`, повторный запрос, отмена в очистке эффекта |
| `src/components/TaskForm.tsx` | `select` тега, сообщения о состоянии, кнопки «Повторить» и «Обновить справочник», блокировка сохранения |

В `Task.tag` хранится **`id`** тега (например, `study`), в форме показывается `name` («Учёба»). Если сохранённый `id` не найден в справочнике, форма показывает сообщение и не подставляет другой тег автоматически. Недоступность справочника блокирует только сохранение формы; просмотр списка, переходы, отмена и удаление работают. Повтор запроса и обновление справочника не сбрасывают введённый черновик.

## Модель доступа (ЛР 6)

**`tags` читают все; `tasks` читает и изменяет только владелец.** Модель совпадает с `supabase/migrations/202611151200_tasks_owner_policies.sql`:

| Таблица | `anon` | `authenticated` | Политики RLS |
|---|---|---|---|
| `tags` | `select` | `select` | `tags are publicly readable` (`select`, `using (true)`) |
| `tasks` | нет прав | `select`, `insert`, `update`, `delete` | четыре отдельные: `tasks select own`, `tasks insert own`, `tasks update own`, `tasks delete own` |

* `owner_id` имеет `default auth.uid()`: клиент владельца не передаёт, база берёт его из проверенного токена;
* `select`, `update`, `delete`: `using ((select auth.uid()) = owner_id)` — доступны только свои существующие строки;
* `insert`: `with check` — нельзя создать строку с чужим `owner_id`;
* `update`: `using` и `with check` совпадают — нельзя изменить чужую строку и нельзя передать свою другому владельцу; для `update` также нужна политика `select`;
* политика `for all` не используется: отдельные правила проще проверять.

`RequireAuth` улучшает сценарий пользователя, но границей безопасности не является: запрос можно отправить и без интерфейса. Данные защищает RLS. Администратор проекта в Dashboard видит строки всех пользователей — это ожидаемо и не доказывает доступ браузера.

## Авторизация и личные записи (ЛР 6)

| Файл | Назначение |
|---|---|
| `supabase/migrations/202611151200_tasks_owner_policies.sql` | `default auth.uid()`, права `authenticated`, четыре политики владельца |
| `src/hooks/useAuth.ts` | состояния `checking` / `guest` / `authenticated`; `onAuthStateChange` + `getSession`, подписка снимается в cleanup |
| `src/app/RequireAuth.tsx` | защищённый маршрут (`Outlet`), статус во время проверки, перенаправление гостя на `/auth` |
| `src/app/AppLayout.tsx` | навигация, email пользователя, «Выйти» (`signOut({ scope: 'local' })`) |
| `src/pages/AuthPage.tsx` | вход и регистрация; проверка пароля (от 8 символов, буква и цифра); `signUp` с `emailRedirectTo`, учёт отсутствия `session`; русские сообщения об ошибках |
| `src/services/tasks.ts` | `getTasks`, `createTask`, `updateTask`, `deleteTask`; преобразование `TaskRow` ↔ `Task`; проверка, что UPDATE/DELETE затронули строку |
| `src/hooks/useTasks.ts` | загрузка списка по `session.user.id`, очистка при выходе и смене пользователя, `reload` и `refresh` |
| `src/components/TasksGate.tsx` | общие состояния «загрузка / ошибка с повтором / данные» для страниц |
| `src/components/TaskForm.tsx` | асинхронный `onSave`, `pending`, `submitError`, защита от повторной отправки |
| `src/lib/supabase.ts` | к ЛР 5 добавлен `requireSupabase()` для сервисов |

Что сделано иначе, чем в тексте методички, и почему:

* маршруты импортируются из `react-router` (так в проекте с ЛР 2), а не из `react-router-dom`;
* имя миграции `202611151200_…`, а не `202609220001_…`: метка времени должна быть больше, чем у `202610242011_initial_schema.sql`, иначе при сортировке по имени миграции окажутся в неверном порядке;
* `supabase` может быть `null` при ошибке настройки (решение ЛР 5): `useAuth` тогда сразу даёт `guest`, `AuthPage` показывает ошибку настройки, сервисы получают клиент через `requireSupabase()`;
* `updateTask` и `deleteTask` запрашивают `select('id')` и считают ноль затронутых строк ошибкой: при RLS чужая и несуществующая строка неотличимы, а интерфейс не должен показывать ложный успех и раскрывать существование чужого id;
* после успешной записи ошибка перезагрузки списка не пробрасывается в форму, а показывается в списке с кнопкой «Повторить»: иначе пользователь повторил бы уже выполненное создание и получил дубль;
* список очищается при смене пользователя во время рендера (`useTasks`), а не в эффекте: это исключает кадр с данными прежнего аккаунта и не нарушает правило `react-hooks/set-state-in-effect`;
* `src/data/tasks.ts` с демонстрационными записями ЛР 2 удалён: они не смешиваются с настоящими и не импортируются.

Подтверждение email: если оно включено в проекте, после `signUp` сессии нет — форма показывает инструкцию «Проверьте почту…», а вход выполняется после подтверждения. Форма не определяет, существует ли аккаунт: сообщение об уже существующем адресе заменено общей формулировкой.

## Проверка двумя аккаунтами

1. Войдите как A, создайте две записи, обновите страницу, измените одну, запишите `id` строки.
2. Выйдите: список очищается, `/tasks/:id` ведёт на `/auth`. Войдите снова как A — записи на месте.
3. Войдите как B: записей A нет. Создайте запись B и обновите страницу.
4. Временно (в коде, под сессией B) запросите `select` с `owner_id` пользователя A, затем `update` и `delete` по `id` строки A, затем `insert` с явным `owner_id` A. Ожидается: пустой результат, ноль затронутых строк, отказ `WITH CHECK` (код `42501`). Проверочный код удалить.
5. Вернитесь к A: записи не изменены, запись B не видна.

Не используйте secret key и `service_role` для этой проверки: они обходят RLS.

## Текущие ограничения

Нет Node API; связанные сущности и поиск по двум параметрам появятся в ЛР 7. Для работы нужны интернет, заполненный `.env.local` и настроенный Supabase Auth (разрешённый redirect URL, подтверждение email по решению преподавателя). Таблицы, кроме `tags` и `tasks`, не используются.

## Использование ИИ

ИИ использовался для объяснения структуры React-проекта, проверки соответствия проекта требованиям лабораторной работы и поиска возможных ошибок. Предложенные изменения были проверены вручную по содержимому проекта, запуску и сборке. В ЛР 5 ИИ использовался для подготовки SQL-миграции, клиента Supabase и документации; пароль базы, secret key, `service_role` и содержимое `.env.local` ИИ не передавались. В ЛР 6 ИИ использовался для подготовки миграции политик владельца, хука `useAuth`, страницы входа, защищённых маршрутов, сервиса задач и документации; пароли, токены и `.env.local` ИИ не передавались. Доступ двумя реальными сессиями (аккаунты A и B) проверяется вручную.
